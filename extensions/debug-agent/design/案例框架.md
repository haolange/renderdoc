# Renderdoc Debug Agent 案例框架



一、核心路线决策：如何让智能体真正“学会”策略

通常所担忧的两点：上下文窗口对系统提示词的限制，以及AI Model仅机械执行预设而非真正理解问题而自发的规划解决方法，已成为调试智能体的核心瓶颈。这里我们提出三阶段演进路线，针对性解决这些问题，确保资源高效投入。

1.1，初始方案：动态知识外置架构

此方案的核心在于将策略知识从单一、庞大的系统提示词中剥离，外置到可动态检索与加载的结构化组件中。

System Prompt：仅包含最通用的元规则，例如“一切结论必须基于证据”、“输出必须为结构化JSON计划”、“工具调用需遵循L0-L5分层规范”、“禁止无证据的推测”。

Skill File：将针对特定场景的标准操作流程（SOP）封装成模块（如NaN处理SOP、几何问题SOP）。系统仅动态加载与当前Bug相关的1-3个技能模块至上下文，从而从根本上解决上下文窗口受限的问题。这一理念与“技能即插件”的思想一致。

Case Library RAG：当新Bug出现时，系统从结构化案例库中检索最相似的3-8个历史案例，并将这些案例的摘要卡片（而非完整详情）注入上下文，作为参考。

Deterministic Executor：计划器（Planner）输出的行动链（Action Chain）由一个确定的编排器（Orchestrator）执行，确保工具层的行为稳定、可预测，避免模型自由发挥导致的漂移。

该路线的最大价值在于无需训练即可快速部署可用系统，并能立即将积累的案例转化为生产力。

后续阶段说明（供未来规划参考）：

第二阶段（可选）：监督微调（SFT）。当积累数百个高质量案例（包含完整的行动链与证据）后，可对计划器进行微调，使其更“原生”地掌握调试策略，例如学习如何为给定Bug选择正确的技能模块。

第三阶段（高级）：基于强化学习的微调（RFT）。仅建议在能精确定义可自动验证的奖励函数（如“用最少步骤定位首次NaN出现的具体事件”）的子任务上使用，成本较高且不稳定。

二、多模态支持策略：结构化优先

对于图形渲染Bug，支持多模态信息是必要的，因为视觉现象难以用文字完全描述。然而，在模型训练和推理时，直接输入原始图像并非最佳选择。

推荐采用“三层多模态结构”以实现规模化应用：

原始资产层：保留PNG截图、视频、RenderDoc捕获文件（.rdc）等原始多模态数据。

派生特征层：从原始资产中提取可量化、结构化的特征，如图片文字描述、关键坐标、颜色直方图摘要、NaN热力图数据、像素历史摘要等。

推理注入层：

对于纯文本模型，注入“派生特征”的文字摘要作为证据。

对于多模态模型，可选择性地注入关键缩略图。

这种方式既保留了多模态真相，又控制了推理时的上下文长度，使系统更具灵活性。

三、 强泛化Bug描述规范

为实现上千案例的量化管理与高效利用，建议将每个案例拆分为两份：

BugFull（完整档案）：用于长期沉淀、复现和作为训练数据集。

BugCard（检索卡片）：BugFull的高度压缩摘要，专门用于运行时RAG检索与上下文注入，以解决窗口限制问题。

3.1，设计哲学：围绕三个抽象轴

本规范的核心泛化能力来源于其不针对具体Bug类型，而是围绕所有渲染Bug共通的三个维度设计：

症状（Symptom）：看到了什么异常现象，在何种条件下出现。

不变量（Invariant）：违反了图形系统中的哪一条基本规则或契约（如“输出值必须有限”、“边界框必须在视锥体内”）。

证据与行动链（Evidence & Action Chain）：使用了哪些确定性工具来生成可复验的证据，以及如何通过一系列步骤排查并定位问题。

3.4，图形不变量库：泛化的基石

为使智能体实现真正的泛化，不应只记忆“Bug类型”，而应理解“违反了什么规则”。建议建立并维护一个图形不变量库，例如：

I-NAN-01：任何输出到可见渲染目标（RT）的像素值必须是有限的（非NaN/Inf）。

I-GEO-01：如果一个物体应当可见，则其裁剪空间边界框必须与视锥体相交。

I-COLOR-01：颜色空间转换（Gamma/Linear）必须恰好执行一次。

每个BugFull都必须关联至少一个被违反的不变量。这为后续的RAG、SFT提供了稳定、抽象的检索和标签体系。

四、落地应用指南

使用本规范收集和管理案例时，遵循以下明确步骤以最大化收益：

初期填充：优先确保每个BugFull填齐最关键的12个字段（如标题、环境、症状描述、证据、根因、修复方法、推荐SOP），其余字段可暂空。

自动生成卡片：开发一个确定性的总结器，根据BugFull自动生成格式统一的BugCard，无需依赖大模型。

立即上线RAG：部署系统，使计划器每次调试时仅接收Top-5个相似BugCard和1-2个相关Skills模块。

积累与微调：当积累500个以上带有完整action_chain的高质量案例后，考虑对计划器进行SFT。

审慎应用RL：仅对“可验证子任务”（如“用最少步骤定位首次NaN事件”）考虑使用强化学习，避免初期追求全覆盖。
