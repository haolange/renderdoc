Renderdoc Debug Agent能力框架
AIRD Framework（Agentic Investigation for Rendering Debugging）是一套系统化的、面向专家级渲染调试的智能化工作流方案。该框架的核心设计理念在于：以不变量（Invariant）驱动推理，以证据（Evidence）驱动实验，以对抗式 Multi-Agent 提升精度与效率，以 BugFull/BugCard 作为量化与沉淀单元。框架不依赖于重新构建新的软件体系，而是将既有的 Skills、MCP Tools、Documentation 以及 Team Agents 等技术组件有机整合，形成一套可复用、可自迭代、可审计的研究式调试工作流。
本方案的核心价值在于将传统的、高度依赖个人经验与直觉的渲染调试过程，转化为一个结构化、可验证、可沉淀的科学研究流程。通过引入图形不变量库（Invariant Library）、标准操作程序库（SOP Library）、项目私有知识插件（Project Plugin Docs）以及多智能体专家团队（Multi-Agent Expert Team）等核心组件，AIRD Framework 实现了从"经验猜测"到"逻辑推理"、从"单点突破"到"系统化协作"、从"知识流失"到"组织资产沉淀"的根本性转变。

## 一， 总体设计目标与核心原则
为了更深入地理解该框架的运作机制与优势，本节将聚焦于其总体设计目标与核心原则。这些目标与原则不仅是框架构建的基石，也确保了其在实践中的可复用性、可审计性及自迭代能力，从而支撑起从“猜测”到“推理”、从“单点”到“系统”的根本转变。接下来，我们将逐一解析这些设计目标与原则的具体内涵及其实现路径。

### 1.1 设计目标
AIRD Framework 的设计围绕四个核心目标展开，这些目标共同构成了框架的价值主张与技术路线。
#### 1.1.1 专家级因果定位

传统调试 vs AIRD 调试方法对比 - 左侧展示传统"猜测式"调试的低效循环，右侧展示 AIRD"推理式"调试的系统化流程
传统的渲染调试往往陷入"猜原因"的困境：工程师基于有限的现象观察与个人经验，提出一个看似合理的假设，然后围绕这个假设进行验证。这种方法的问题在于，一旦初始假设错误，后续的所有努力都可能白费。更严重的是，即使最终找到了一个"看起来有效"的修复方案，也很难确定这个方案是否真正解决了根本问题，还是仅仅掩盖了症状。
AIRD Framework 的第一个核心目标是实现专家级因果定位，即不是"猜原因"，而是建立可被反证、可复现的实验链，最终产出可验证的最小修复（Minimal Patch）。这一目标的实现依赖于以下几个关键机制：
不变量驱动的推理链：通过 Invariant Library 将模糊的"渲染结果不对"转化为精确的"Invariant I-XXX-XX 被违反"，从而建立起从现象到根因的系统化推理路径。例如，当观察到渲染结果出现黑色像素时，不是直接猜测"可能是光照计算错误"，而是首先检查是否违反了 I-NAN-01（禁止 NaN/Inf 值）、I-SHADING-NONNEG-01（着色贡献非负）等不变量。通过识别被违反的不变量，可以快速缩小问题范围，并指向具体的根因机理。

不变量驱动推理链 - 展示如何通过 Invariant 检查将渲染异常现象（黑色像素）映射到精确的根因定位
差分分析优先策略：在进行根因定位时，优先建立 A/B 对照（设备、开关、Pass、Shader Variant、Precision Fence 等），通过"差分证据"压缩搜索空间。例如，当一个渲染问题只在特定 GPU 上出现时，通过对比该 GPU 与正常 GPU 的渲染管线状态、Shader 编译结果、驱动行为等，可以快速定位到平台相关的根因。差分分析的核心价值在于，它能够有效排除大量的"无关变量"，使得调查聚焦于真正的差异点。
反事实验证强制约束：任何根因结论都必须配套反事实验证（Counterfactual Test），即通过最小 Patch、开关验证、重放验证等方式，证明"如果修复了这个根因，问题就会消失"。只有满足了这一验证要求，才允许将结论写入 BugFull 的 root_cause 和 fix 字段，并生成相应的 BugCard。这种强制约束确保了所有输出的根因分析都是经过严格验证的，而非基于未经证实的假设。
通过这三个机制的协同作用，AIRD Framework 能够实现真正的专家级因果定位，确保每一个根因结论都是可靠的、可验证的、可复现的。
#### 1.1.2 跨项目泛化
渲染调试的一个核心挑战在于，不同项目的渲染管线、材质系统、资源组织方式往往存在巨大差异。一个针对特定项目定制的调试工具或流程，很难直接应用到其他项目。这导致了大量的重复性工作，以及知识沉淀的困难。
AIRD Framework 的第二个核心目标是实现跨项目泛化，即框架对任意项目成立，项目私有知识以"插件 Docs"挂载，不污染框架核心。这一设计理念的核心在于将通用的调试逻辑与项目特定的知识进行解耦。
通用框架层：包括 Invariant Library、SOP Library、Multi-Agent 协作机制、BugCard/BugFull 数据结构等，这些组件是项目无关的，代表了渲染调试的通用方法论与工具链。例如，I-NAN-01（禁止 NaN/Inf 值）这一不变量，对于任何使用浮点计算的渲染管线都是成立的，无论是移动端的前向渲染还是 PC 端的延迟渲染。
项目插件层：包括项目特定的材质模块化定义、Block 计算指纹、资源映射关系等，这些知识以标准化的插件接口挂载到框架中。例如，一个使用虚幻引擎的项目可能定义了 CharacterSkinBlock、WorldTerrainBlock 等材质模块，每个模块都有其特定的 HLSL 表达式指纹。当框架在分析 Shader IR 时，可以通过查询项目插件，将抽象的 IR 指令映射回具体的材质模块，从而快速定位问题。
通过这种分层设计，AIRD Framework 能够在保持核心逻辑通用性的同时，灵活适配不同项目的特定需求。

跨项目泛化架构 - 展示通用框架层与项目插件层的解耦设计，说明框架如何通过插件接口适配不同项目
当应用到新项目时，只需要编写相应的项目插件，而无需修改框架核心，从而大大降低了迁移成本，提高了知识复用效率。
#### 1.1.3 全链路可追溯
在复杂的调试过程中，往往涉及大量的工具调用、数据分析、假设验证等操作。如果这些操作没有被系统化地记录，那么当调试结束后，很难回溯整个过程，理解为什么做出了某个决策，或者验证某个结论的可靠性。这不仅影响了知识的沉淀，也使得调试过程难以审计与优化。
AIRD Framework 的第三个核心目标是实现全链路可追溯，即所有关键工具调用与输出都落地到可审计的 action_chain 与 evidence，形成可学习的数据闭环。
Action Chain 记录机制：每一次 Agent 调用工具、执行分析、做出决策，都会被记录到 Action Chain 中。每条记录包含 agent_id（执行者）、tool_name（工具名称）、tool_parameters（调用参数）、start_timestamp / end_timestamp（时间戳）、result_status（执行结果）、output_evidence_refs（产出的证据引用）、decision_context（决策依据）等详细信息。这种记录机制使得整个调试过程变得透明、可审查。
Evidence 结构化要求：每条证据都必须携带 source_tool（来源工具）、parameters（生成参数）、data_payload（实际数据）、timestamp（时间戳）、environment_context（环境上下文）等结构化字段。这种设计确保了证据的可追溯性与可复现性。任何人都可以根据 Evidence 记录，重新调用相同的工具与参数，验证证据的有效性。
数据闭环与学习：通过将 Action Chain 与 Evidence 进行关联，可以构建出完整的"决策→执行→观测→结论"闭环。这些数据不仅用于审计，更是 Agent 学习与 SOP 进化的核心素材。例如，通过分析大量成功的 Action Chain，可以提取出高效的工具调用模式，并将其固化为新的 SOP；通过分析失败的 Action Chain，可以识别无效的决策路径，并优化 Agent 的策略。
全链路可追溯不仅提升了调试过程的透明度与可信度，更为框架的持续优化与智能化提供了数据基础。

#### 1.1.4 自迭代能力
传统的调试工具与流程往往是静态的：一旦设计完成，就很难根据实际使用情况进行优化。这导致了工具的效率难以提升，知识的积累难以转化为能力的增长。
AIRD Framework 的第四个核心目标是实现自迭代能力，即随着 Debug 增多，自动产生更多 BugCard/BugFull、SOP（Skills）以及项目插件 Docs 的增量，持续提高命中率与收敛速度。
BugCard/BugFull 的自动生成与积累：每一次成功的调试，都会产生一个 BugFull 记录（完整的研究报告）以及一个 BugCard（快速检索快照）。这些记录会被自动索引，并加入到知识库中。当下次遇到类似问题时，系统可以通过检索 BugCard，快速定位到相关的历史案例，并复用其解决方案。随着案例的积累，知识库的覆盖范围不断扩大，命中率持续提升。
SOP 的自动提取与进化：通过分析大量 BugFull 中的 Action Chain，系统可以识别出高频、高效的工具调用模式，并自动提取为新的 SOP。例如，如果发现在处理 I-PREC-01 违反时，成功的案例都遵循了"SPIR-V Decoration 扫描 → HLSL Mapping 分析 → Precision Fence 应用"这一流程，那么系统可以将这一流程固化为 SOP_Precision_RelaxedPrecision_v2，并在后续遇到类似问题时自动推荐。
项目插件的增量更新：随着对项目的深入理解，项目插件中的材质模块定义、Block 指纹、资源映射等知识会不断丰富与完善。例如，当发现某个新的材质模块导致了渲染问题时，可以将该模块的定义与指纹加入到项目插件中，从而提升后续调试的效率。
通过这三个层面的自迭代，AIRD Framework 能够实现"用得越多，越智能"的正向循环，持续提升调试效率与质量。

### 1.2 三条"专家行为"约束（强约束）
为了确保 AIRD Framework 的调试过程符合专家级标准，框架引入了三条强约束，这些约束是对所有 Agent 行为的刚性要求。
#### 1.2.1 不以现象推断原因
在传统的调试过程中，工程师往往会根据观察到的现象，直接推断可能的原因。例如，看到渲染结果出现黑色像素，就猜测"可能是光照计算错误"或"可能是纹理采样错误"。这种推断虽然直观，但往往缺乏严谨性，容易导致错误的归因。
AIRD Framework 的第一条强约束是：现象描述与原因推断必须隔离；先"观测与分类"，后"假设与验证"。
观测与分类阶段：在这一阶段，Agent 的职责是客观地记录观察到的现象，并将其归入预定义的症状分类学（Symptom Taxonomy）。例如，观察到"渲染结果出现黑色像素"，应该被标记为 symptom_tags: [黑色像素， 局部异常]，而不是直接推断"光照计算错误"。BugFull 规范明确要求 observed 字段只描述现象，不包含任何原因推断。
假设与验证阶段：在完成现象分类后，Agent 才可以基于 Invariant Library 与历史案例，提出可能的根因假设，并设计实验进行验证。例如，针对"黑色像素"现象，可以提出假设"违反了 I-NAN-01（禁止 NaN/Inf 值）"，然后通过 NaN Heatmap 生成、Pixel History 追溯等工具进行验证。
这种隔离机制确保了调试过程的严谨性，避免了"先入为主"的确认偏见（Confirmation Bias），使得每一个根因结论都是基于证据的，而非基于直觉的。
#### 1.2.2 先做差分（Differential Debugging）
在面对复杂的渲染问题时，搜索空间往往非常巨大：可能是 Shader 代码错误，可能是资源数据异常，可能是驱动 Bug，也可能是硬件特性导致的。如果盲目地逐一排查，效率会非常低下。
AIRD Framework 的第二条强约束是：尽量建立 A/B 对照（设备、开关、Pass、Shader Variant、Precision Fence），优先用"差分证据"压缩搜索空间。
差分分析的核心思想：通过构建两个尽可能相似、但在某个关键维度上存在差异的场景（A 与 B），然后对比它们的渲染结果、中间状态、工具输出等，从而快速定位到导致问题的关键因素。
常见的差分维度：
设备差分：对比问题设备与正常设备的渲染结果，定位平台相关的 Bug。例如，某个渲染问题只在 Adreno GPU 上出现，通过对比 Adreno 与 Mali GPU 的 Shader 编译结果、驱动行为等，可以快速定位到 Adreno 特定的精度降低（Precision Lowering）问题。
开关差分：通过开启/关闭某个渲染特性（如 MSAA、HDR、后处理效果等），观察问题是否消失，从而定位到相关的渲染模块。
Pass 差分：对比不同渲染 Pass 的输出，定位到第一个出现异常的 Pass，从而缩小问题范围。
Shader Variant 差分：对比不同 Shader 变体（如不同的宏定义、不同的优化级别）的行为，定位到导致问题的具体代码路径。
Precision Fence 差分：通过在 Shader 中插入精度围栏（Precision Fence），强制某些计算使用高精度，观察问题是否消失，从而验证精度相关的假设。
差分分析的核心价值在于，它能够将一个复杂的、多变量的问题，转化为一个简单的、单变量的问题，从而大大提高调试效率。
#### 1.2.3 根因必须配套反事实验证（Counterfactual Test）
即使通过严谨的推理与差分分析，得出了一个看似合理的根因结论，也不能保证这个结论是正确的。只有通过反事实验证，即证明"如果修复了这个根因，问题就会消失"，才能确认根因的有效性。
AIRD Framework 的第三条强约束是：最小 Patch / 开关验证 / 重放验证至少满足一种，才允许把结论写入 BugFull 的 root_cause / fix，并生成 BugCard。
最小 Patch 验证：针对识别出的根因，设计一个最小的代码修改（Minimal Patch），然后验证这个修改是否能够解决问题。例如，如果根因是"对零向量进行归一化导致 NaN"，那么最小 Patch 可能是将 normalize(v) 替换为 SafeNormalize(v)（在归一化前检查向量长度）。如果应用这个 Patch 后问题消失，则证明根因是正确的。
开关验证：通过开启/关闭某个特性或配置，验证根因假设。例如，如果怀疑问题是由 RelaxedPrecision 导致的精度降低引起的，可以通过编译选项强制关闭 RelaxedPrecision，观察问题是否消失。
重放验证：在修复后，重新执行原始的复现步骤，验证问题是否确实被解决，且没有引入新的问题（回归测试）。
只有通过了反事实验证，才能将根因结论与修复方案写入 BugFull，并生成相应的 BugCard。这一强约束确保了所有输出的知识都是经过严格验证的，避免了未经证实的"猜测"污染知识库。


BugCard 与 BugFull 双层知识存储体系 - 展示轻量级快照（BugCard）与完整研究报告（BugFull）的定位差异与引用关系

## 二，基础数据结构：BugCard / BugFull 作为"量化单元 + 知识存储单元"
AIRD Framework 的知识沉淀与复用，依赖于两个核心数据结构：BugCard 与 BugFull。这两者构成了一个双层的知识存储体系，分别服务于"快速检索与路由"以及"深度分析与学习"两个不同的场景。

### 2.1 BugCard：面向检索与路由的知识快照
BugCard 在 AIRD Framework 中被定位为一种高度浓缩且可快速复用的知识单元，其核心功能在于将复杂的渲染调试案例抽象为结构化的"快照"。这种设计旨在显著提升调试知识的检索效率与问题路由的准确性，从而加速问题解决流程并降低对专家经验的依赖。
BugCard 的设计哲学围绕"快速复用"展开，其价值体现在将复杂、耗时的调试过程压缩为一系列可检索的路由键（Routing Key）。这不仅是对单个 Bug 案例的记录，更是对问题解决路径的模式化提炼。其核心价值链条可概括为：
症状 (Symptom) + 触发条件 (Trigger) → 不变量 (Invariant) → 标准操作程序 (SOP) → 工具链 (Action Chain)
这一链条为调试人员提供了一个清晰、高效的导航路径，使其能够从观察到的现象出发，快速定位到潜在的根本原因，并获取相应的解决方案。
#### 2.1.1 BugCard 的关键字段

BugCard 核心字段与关系 - 展示 BugCard 的字段分组（分类层、症状层、定位层、解决层、证据层）及其逻辑关系
BugCard 的结构化设计是其实现高效检索与路由的基础。
以下是其典型字段的详细说明：
bug_family：用于对 Bug 进行宏观分类的标识符，代表一类具有相似性质或影响范围的问题。通常采用预定义的枚举值或层级分类体系（如 Rendering.Lighting， Rendering.Shadows， Performance.GPU， Data.Corruption）。这种分类有助于在早期阶段缩小问题范围，并为后续的自动化分析提供上下文。
invariants_broken：明确指出该 Bug 案例中被违反的 Invariant（不变量）的唯一标识符列表。Invariant 是 AIRD Framework 的核心概念之一，代表了渲染管线中在特定阶段或条件下必须保持的属性或关系。例如，I-NAN-01 可能表示"渲染结果中不应出现 NaN 值"，I-PREC-01 可能表示"特定计算的精度应在允许误差范围内"。通过识别被违反的 Invariant，可以直接指向问题的本质，而非仅仅停留在表面现象。
symptom_tags：描述 Bug 表现形式的关键词或标签集合。这些标签可以是视觉上的（如 黑色像素， 闪烁， 纹理错误， 光照异常），也可以是性能上的（如 帧率骤降， 卡顿）或其他非视觉表现。symptom_tags 旨在提供对 Bug 现象的快速、直观描述，便于人工识别与初步筛选。
trigger_tags：描述触发 Bug 发生的特定条件或环境因素的关键词或标签集合。触发条件可能包括特定的硬件平台（如 Adreno GPU， Intel iGPU），驱动版本（如 Driver_v510），操作系统（如 Windows 11， Android 13），游戏内特定场景（如 夜间场景， 雨天效果），特定的渲染特性（如 Tessellation， RayTracing），甚至特定的输入数据或用户操作。
anchor：指向 Bug 首次被检测到或表现异常的关键位置或时间点。anchor 可以是一个渲染管线中的特定 Pass/Event（如 DeferredShadingPass， PostProcessBloom），一个具体的 Draw Call ID，一个像素坐标（[x， y]），一个特定的着色器阶段（如 VertexShader， FragmentShader），甚至是一个代码文件路径与行号。anchor 的精确性直接影响到调试的效率，它为后续的 Pixel History 或 命令列表/事件流（Native Command List / Event Stream）分析提供了起点。
key_evidence：与 Bug 相关的最关键的证据集合，用于支持根因分析与复现。key_evidence 可以是多种形式的调试数据，例如渲染帧截图、渲染管线状态快照、Buffer/Texture Dump、Shader 输出、Call Stack、日志片段等。
root_cause_one_liner：对 Bug 根本原因的简洁、一句话描述。这个字段要求高度凝练，直接指出导致 Bug 的核心技术问题。例如："着色器中对 UNorm 纹理的错误解包导致光照计算溢出"，"由于 RelaxedPrecision 修饰符在 Adreno GPU 上导致浮点精度不足"。
fix_one_liner：对 Bug 修复方案的简洁、一句话描述。与 root_cause_one_liner 对应，fix_one_liner 描述了解决该 Bug 的核心改动。例如："修正 UNorm 纹理解包逻辑，使用正确的转换函数"，"调整着色器，避免在关键计算中使用 RelaxedPrecision"。
recommended_sop：指向与该 Bug 案例最相关的 SOP（Standard Operating Procedure）的标识符。SOP 是 AIRD Framework 中的技能模块，代表了一套经过验证的、用于解决特定类型问题的标准流程或工具链。
#### 2.1.2 BugCard 的检索与路由机制
BugCard 的核心价值在于其作为检索与路由键的能力。当一个新的 Bug 案例出现时，系统或工程师可以通过以下机制利用 BugCard 库：
多维度检索：工程师可以根据观察到的 symptom_tags、trigger_tags，或通过初步分析识别出的 invariants_broken 来检索相关的 BugCard。例如，当发现渲染结果出现 黑色像素 且发生在 Adreno GPU 上时，可以组合这些标签进行检索。
相似性匹配与推荐：系统可以利用机器学习算法，根据新 Bug 的特征（如日志模式、崩溃堆栈、初步诊断结果）与现有 BugCard 的字段进行相似性匹配，推荐最可能相关的历史案例。
智能路由：一旦识别出相关的 BugCard，其内嵌的 recommended_sop 字段将直接引导工程师进入相应的标准操作流程。这可能包括启动特定的调试工具、执行一系列诊断步骤，或调用预设的 Action Chain。
知识图谱构建：通过 BugCard 之间的关联（例如，多个 BugCard 指向同一个 SOP，或同一个 bug_family 下有多个变种），可以构建一个动态的知识图谱，揭示不同 Bug 类型之间的关系，进一步优化检索与路由的效率。

### 2.2 BugFull：可复现研究报告的数据结构与核心机制
BugFull 在 AIRD Framework 中被定义为一种可复现研究报告（Reproducible Research Report），其核心价值在于提供一个全面、严谨且可追溯的调试与分析记录。与 BugCard 侧重于快速检索和问题路由不同，BugFull 的设计目标是实现对渲染异常的严谨闭环（Rigorous Closed-Loop），并作为 AIRD Framework 持续自迭代（Self-Iterative）的素材（Material）。
BugFull 作为"完整研究记录"的定位，使其在以下三个关键方面发挥作用：
复现（Reproduction）：BugFull 旨在提供足够详细且结构化的信息，以确保任何人在任何时间都能精确地复现原始的渲染异常。这对于验证修复方案、进行回归测试以及深入分析问题根源至关重要。在复杂的渲染管线中，一个微小的状态差异都可能导致完全不同的渲染结果，因此 BugFull 必须捕获所有相关的上下文信息，包括但不限于 GPU 状态、API 调用序列、资源内容和时间戳。
审计（Auditing）：BugFull 记录了从问题发现到解决的整个过程，包括所有中间步骤、决策依据和工具调用。这使得整个调试流程变得透明、可审查，有助于团队协作、知识共享和质量控制。通过审计，工程师可以回溯问题解决的路径，理解决策背后的逻辑，并识别潜在的流程改进点。
训练（Training）：BugFull 将每一次成功的调试经验转化为结构化的数据，为 AIRD Framework 中的 Agent 学习和 SOP 进化提供高质量的训练样本。通过对大量 BugFull 数据的分析，系统能够识别常见的模式、优化调试策略，并提升自动化解决问题的能力。
#### 2.2.1 Evidence 结构化：可复用观测路径的构建

Evidence 结构化要素 - 展示 Evidence 的关键字段（source_tool、parameters、data_payload、timestamp、environment_context）及其可追溯性设计
Evidence（证据）是 BugFull 的基石，它代表了在调试过程中获取的任何形式的观测数据。为了确保 Evidence 的有效性、可追溯性和可复用性，AIRD Framework 强制要求每条 Evidence 必须进行严格的结构化。其核心原则是：每条证据必须携带来源工具与参数，从而形成可复用的观测路径。
一条典型的 Evidence 记录应包含以下关键结构化要素：
source_tool：明确指出生成该证据的工具名称或标识符。这不仅包括商业调试工具（如 RenderDoc、PIX、GPUView），也涵盖了项目内部开发的诊断工具、自定义脚本或日志系统。精确的 source_tool 记录是理解证据生成环境和方法的基础，也是自动化重现证据获取过程的入口。
parameters：记录调用 source_tool 时使用的所有输入参数。这些参数是重现证据生成过程的关键，必须足够详细和精确，以确保每次调用都能得到一致的结果。具体参数类型包括图形 API 调用参数、渲染状态快照、资源标识符与内容、时间戳与帧号、屏幕空间坐标或区域、查询条件与过滤器等。
data_payload：实际的证据数据。这可以是多种形式，根据 source_tool 和 parameters 的不同而异，并且通常以文件路径或序列化数据块的形式存储。具体类型包括图像数据、二进制数据、文本数据、结构化数据等。
timestamp：证据生成的时间戳，用于时间序列分析和事件排序，尤其是在多线程或异步操作中。精确的时间戳有助于构建事件的时序图，从而揭示潜在的竞态条件或依赖关系。
environment_context：捕获证据时的系统环境信息，包括操作系统版本、驱动版本、硬件型号、应用程序版本、编译器版本、SDK 版本等。这些信息对于确保复现环境的一致性和诊断环境相关问题至关重要。
通过将 source_tool 和 parameters 与 data_payload 绑定，AIRD Framework 能够构建出可复用的观测路径。这意味着，如果需要重新生成或验证某条证据，系统可以直接调用相应的 source_tool 并传入记录的 parameters，从而精确地重现当时的观测结果。这种机制带来了自动化验证与回归测试、知识沉淀与泛化、差分分析的精确性、降低复现成本、支持反事实验证、促进协作与知识共享等显著优势。
#### 2.2.2 Action Chain 记录：策略学习与 SOP 进化的核心
Action Chain（工具调用链）是 BugFull 的另一个神经中枢，它记录了 AIRD Framework 中的 Agent 在调试过程中实际执行的所有工具调用序列。Action Chain 的核心作用在于固化真实执行的工具调用链，用于后续策略学习与 SOP 进化。
Action Chain 记录的是一系列离散的操作（Actions），每个操作都代表了 Agent 对外部工具或内部模块的一次调用。每个操作应包含以下详细信息：
agent_id：执行该操作的 Agent 标识符，例如 Triage & Taxonomy Agent、Capture & Repro Agent、Pixel/Value Forensics Agent、Shader & IR Agent。这有助于追溯是哪个智能体执行了何种操作，并分析不同 Agent 之间的协作模式和职责边界。
tool_name：被调用的工具名称，可以是外部调试工具（如 RenderDoc API、D3D12 Debug Layer）、内部分析模块（如 Invariant Checker）、自定义脚本或预定义的 SOP。工具名称应具有唯一性，以便系统识别和调用。
tool_parameters：调用工具时传入的具体参数。与 Evidence 中的 parameters 类似，但更侧重于指令而非观测。这些参数是重现 Agent 决策的关键。
start_timestamp / end_timestamp：操作的开始和结束时间，用于性能分析、时序分析以及评估 Agent 的决策效率。长时间运行的操作可能需要进一步优化或分解。
result_status：操作的执行结果，例如 Success、Failure、Timeout、Partial Success。这对于评估 Agent 的决策质量和工具的可靠性至关重要。
output_evidence_refs：该操作所产生的 Evidence 记录的引用列表。这建立了 Action Chain 与 Evidence 之间的直接关联，使得可以追溯每个操作的产出。
decision_context：记录 Agent 在执行此操作时的决策依据，例如当前的问题状态、已有的 Evidence、Invariant 检查结果、以及其内部的推理过程。这对于理解 Agent 的行为逻辑和进行后续的策略优化非常重要。
通过对 Action Chain 的分析，AIRD Framework 能够实现策略学习与 SOP 进化。系统可以识别成功的调试模式，提取高效的工具调用序列，并将其固化为可复用的 SOP。同时，通过分析失败的 Action Chain，系统能够识别无效的决策路径，并优化 Agent 的决策策略。
#### 2.2.3 BugFull 的必备字段与扩展机制
BugFull 必须具备以下核心字段，以确保其作为完整研究记录的功能：
root_cause.invariant_broken：明确指出被违反的 Invariant ID，建立问题与不变量之间的直接关联。这是从现象到本质的关键桥梁。
root_cause.category_primary：问题的主要分类，例如 Shader Logic Error、Driver Bug、Precision Issue、Resource Management Error 等。这有助于对问题进行宏观归类，并支持统计分析。
root_cause.blame(location)：精确指出问题发生的位置，可以是代码文件路径与行号、特定的 Shader 函数、渲染 Pass 名称、或 GPU 驱动模块等。这为修复提供了明确的目标。
fix.fix_type：修复方案的类型，例如 Code Patch、Configuration Change、Workaround、Driver Update 等。这有助于分类管理修复方案，并评估不同类型修复的有效性。
fix.summary：对修复方案的简要描述，说明修改了什么、为什么这样修改、以及预期的效果。在真实案例中，这通常会扩展为完整的 patch diff（代码差异）和 verification plan（验证计划）。
BugFull 的设计支持灵活的扩展机制。除了上述核心字段，可以根据项目需求添加自定义字段，例如 performance_impact（性能影响评估）、affected_platforms（受影响的平台列表）、related_bugs（相关 Bug 的引用）等。这种扩展性确保了 BugFull 能够适应不同项目的特定需求，同时保持核心结构的一致性。
通过 BugCard 与 BugFull 的双层结构，AIRD Framework 实现了调试知识的高效管理与深度沉淀。BugCard 用于"快速命中"，支持问题的快速检索与路由；BugFull 用于"严谨闭环 + 自迭代素材"，支持问题的精确复现、全流程审计以及智能体的持续学习。

## 三，知识层：Invariant / SOP / Project Plugin 三类知识对象
AIRD Framework 的知识层是其智能化的核心基础，由三类关键知识对象构成：Invariant Library（图形不变量库）、SOP Library（技能模块库）以及 Project Plugin Docs（项目私有知识插件）。这三者共同形成了一个层次化、可扩展的知识体系，支撑着框架从现象观测到根因定位、再到修复方案产出的完整推理链条。


### 3.1 Invariant Library：用不变量替代经验猜测
"像专家一样 Debug"的第一性原理可以归结为：用不变量替代经验猜测。Invariant（不变量）代表了渲染管线中在特定阶段或条件下必须保持的数学或逻辑属性。当一个 Invariant 被违反时，即提供了明确的异常信号，从而驱动后续的调查方向。
传统的调试方法往往依赖于工程师的经验与直觉："这个黑色像素可能是光照计算错误"、"这个闪烁可能是资源同步问题"。这种方法的问题在于，经验是主观的、难以量化的、难以传承的。不同的工程师可能对同一个现象有完全不同的解读，导致调试效率低下、知识难以沉淀。
Invariant Library 的引入，将这种主观的"经验猜测"转化为客观的"逻辑推理"。每个 Invariant 都是一个明确的、可验证的断言，例如：
I-NAN-01：渲染管线输出不得出现 NaN 或 Inf 值
I-PREC-01：精度降低（Precision Lowering）不得改变数值的符号或有效范围
I-SHADING-NONNEG-01：着色贡献（Diffuse， Specular）不得为负值
I-LIGHT-UNPACK-01：UNorm 格式纹理解包后的结果应在 [0，1] 范围内
当观察到渲染异常时，不是直接猜测原因，而是首先检查哪些 Invariant 被违反了。通过识别被违反的 Invariant，可以快速缩小问题范围，并指向具体的根因机理。
#### 3.1.1 Invariant 条目的结构化定义
每个 Invariant 条目应包含以下结构化字段，以确保其可用性、可验证性与可扩展性：
id：不变量的唯一标识符，采用统一的命名规范，例如 I-NAN-01、I-PREC-01、I-SHADING-NONNEG-01、I-LIGHT-UNPACK-01。这种命名规范便于快速识别不变量的类型和领域。
definition：不变量的精确定义，描述其约束的具体内容。例如："渲染管线输出不得出现 NaN 或 Inf 值"、"着色贡献（Diffuse， Specular）不得为负值"、"UNorm 格式纹理解包后的结果应在 [0，1] 范围内"、"精度降低（Precision Lowering）不得改变数值的符号或有效范围"。定义应具备明确性和可验证性，避免模糊表述。
detection_tests：用于检测该不变量是否被违反的可执行测试方法。例如，对于 I-NAN-01，检测方法可能包括 NaN Heatmap 生成、Pixel History 追溯、数值范围检查等；对于 I-PREC-01，可能包括 SPIR-V Decoration 扫描、精度标注验证等。这些测试方法应是自动化的，能够被 Agent 直接调用。
typical_root_causes：该不变量被违反时的常见根因机理。例如，I-NAN-01 的常见根因包括 normalize(0)（对零向量归一化）、half overflow（半精度浮点溢出）、division by zero（除零错误）等；I-PREC-01 的常见根因包括 RelaxedPrecision lowering（SPIR-V 精度修饰符导致的精度降低）、格式/色彩空间错误等。这些根因为 Agent 提供了初步的假设方向。
fix_patterns：针对该不变量违反的常见修复模式。例如，对于 I-NAN-01，修复模式可能包括 SafeNormalize（安全归一化函数）、Clamp（数值钳位）、CastToFloat（强制转换为高精度浮点）等；对于 I-PREC-01，修复模式可能包括 PrecisionFence（精度围栏）、RangeHardening（范围加固）等。这些模式是经过验证的、可复用的修复策略。
linked_sop：推荐的 SOP（Standard Operating Procedure）标识符，指向专门用于诊断和修复该不变量违反的标准流程。例如，I-NAN-01 可能链接到 SOP_NaN_Diffusion，I-PREC-01 可能链接到 SOP_Precision_RelaxedPrecision_Adreno。
example_cards：相关 BugCard 的索引列表，提供该不变量在实际案例中的应用示例。这些案例为 Agent 提供了学习样本，帮助其理解不变量的实际应用场景。
#### 3.1.2 真实案例：不变量驱动的调试流程
BugCard/BugFull 已经在真实案例中把"不变量→证据→修复"串起来，以下是两个典型案例：
案例 1：I-NAN-01 违反导致的黑色像素问题
现象：渲染结果出现局部黑色像素
Invariant 检测：通过 NaN Heatmap 生成，发现黑色像素区域对应 NaN 值
Pixel History 追溯：追溯到第一个产生 NaN 的 Draw Call，定位到光照计算着色器
根因定位：发现着色器中对法线向量进行归一化时，未检查向量长度，导致 normalize(0) 产生 NaN
修复方案：将 normalize(v) 替换为 SafeNormalize(v)，在归一化前检查向量长度
反事实验证：应用修复后，NaN Heatmap 显示 NaN 值消失，渲染结果恢复正常
路由 SOP：SOP_NaN_Diffusion
案例 2：I-PREC-01 违反导致的精度损失问题
现象：在 Adreno GPU 上，渲染结果出现颜色异常
Invariant 检测：通过 SPIR-V Decoration 扫描，发现关键计算使用了 RelaxedPrecision 修饰符
差分分析：对比 Adreno 与 Mali GPU 的 SPIR-V 编译结果，发现 Adreno 驱动对 RelaxedPrecision 的处理更激进，导致精度降低
HLSL Mapping 分析：追溯到 HLSL 源码中使用了 half 类型，被编译器映射为 RelaxedPrecision
根因定位：half 类型在 Adreno GPU 上精度不足，导致光照计算溢出
修复方案：将关键计算的 half 类型替换为 float，或使用 Precision Fence 强制高精度
反事实验证：应用修复后，在 Adreno GPU 上重新测试，颜色异常消失
路由 SOP：SOP_Precision_RelaxedPrecision_Adreno
这两个案例充分展示了 Invariant Library 的核心价值：将模糊的"渲染结果不对"转化为精确的"Invariant I-XXX-XX 被违反"，从而建立起从现象到根因的系统化推理路径。

### 3.2 SOP Library：可执行策略模板
每个 SOP（Standard Operating Procedure）是一个可执行策略模板（Skills），代表了一套经过验证的、用于解决特定类型问题的标准流程或工具链。SOP 的核心价值在于将成功的调试经验固化为可复用的流程模板，使得 Agent 能够快速应用已验证的策略，避免重复探索。
#### 3.2.1 SOP 的核心内容
每个 SOP 应包含以下核心内容：
触发条件（Trigger Conditions）：描述何时应该启用该 SOP，通常由 symptom_tags + trigger_tags + environment 组合定义。例如，SOP_Precision_RelaxedPrecision_Adreno 的触发条件可能是：症状包含"精度损失"或"颜色异常"，触发环境为 Adreno GPU，且初步分析识别出 I-PREC-01 被违反。
目标 Invariant 集合（Target Invariants）：该 SOP 旨在验证或修复的 Invariant 列表。这明确了 SOP 的目标范围，避免盲目执行。
推荐工具链（Recommended Tool Chain）：SOP 执行过程中应依次调用的工具序列，包括工具名称、调用顺序以及终止条件。例如，SOP_NaN_Diffusion 的工具链可能包括：(1) NaN Heatmap 生成 → (2) Pixel History 追溯 → (3) Shader IR 分析 → (4) 根因定位 → (5) SafeNormalize 应用 → (6) 反事实验证。每个步骤都有明确的输入、输出和成功标准。
输出要求（Output Requirements）：该 SOP 必须产出的 Evidence 类型以及必须完成的反事实验证类型。例如，必须产出 first_bad_event 的 Pixel History 证据，必须完成最小 Patch 验证。这确保了 SOP 执行的完整性和严谨性。
#### 3.2.2 SOP 的可复用性与进化
BugFull 规范本身就为 SOP 提供了挂钩：generalization.recommended_sop + recommended_tools。真实案例也体现了 SOP 的"可复用性"：两个 Adreno 案例都路由到 SOP_Precision_RelaxedPrecision_Adreno，并推荐 ShaderStaticScan / SPIRVDecorationScan / DeviceA_B_Compare。
随着 BugFull 的积累，系统能够自动提取高效的 Action Chain 并生成新的 SOP，从而实现知识的持续进化。例如，如果发现在处理 I-PREC-01 违反时，成功的案例都遵循了"SPIR-V Decoration 扫描 → HLSL Mapping 分析 → Precision Fence 应用"这一流程，那么系统可以将这一流程固化为 SOP_Precision_RelaxedPrecision_v2，并在后续遇到类似问题时自动推荐。

### 3.3 Project Plugin Docs：项目私有知识插件
Project Plugin Docs 保持"可插拔"特性，不进入框架核心，从而确保框架的通用性。这部分包含项目特定的渲染管线知识。
主要内容包括：
材质模块化数据流定义：描述项目中 Character / World / Effect 等不同类型资产的材质模块化结构。例如，一个角色材质可能由 Base Color Block、Normal Block、Roughness Block、Emission Block 等多个模块组成，每个模块负责特定的视觉效果计算。
Block 计算指纹：每个 Block 的"计算指纹"，即其 HLSL/IR 的表达式或关键子图。这些指纹用于从截帧的 Shader/IR 中反推"项目里是哪一个 Block 出问题了"。例如，通过识别特定的 HLSL 函数调用模式或 IR 指令序列，可以定位到具体的材质模块。
Block 与引擎资源映射：Block 与 engine 资源/材质实例/参数的映射关系。这使得 Agent 能够从底层的 Shader 代码追溯到高层的材质资产和参数配置，从而快速定位问题的来源。
项目特定 Invariant：针对项目特定渲染管线或美术风格的不变量定义。例如，某个项目可能要求所有角色材质的金属度（Metallic）值必须在 [0， 0.9] 范围内，以保持美术风格的一致性。
项目插件的接口设计：
框架只规定插件接口，不规定插件内容，从而保证泛化能力。插件接口可能包括：查询 Block 定义、根据 Shader 指纹反推 Block、获取资源映射关系等标准化 API。这种设计使得 AIRD Framework 能够适配任意项目，同时保持核心逻辑的通用性。
Project Plugin Docs 是 AIRD Framework 知识层的重要组成部分，它通过引入可插拔的、项目私有知识扩展机制，极大地增强了框架的灵活性、适应性和泛化能力。通过将通用分析能力与项目特有知识解耦，AIRD Framework 实现了在不同项目之间的高效复用，并有效降低了维护成本，是构建智能渲染调试工作流的关键一环。

## 四，协作层：基于 Multi-Agent 专家团队的协作与审查机制
AIRD Framework 的核心不仅在于其结构化的知识与强大的工具集，更在于其独特的协作模式。框架将复杂的渲染调试任务解构，并通过一个由多个高度专业化的 AI Agent 组成的"专家团队"（Team Agents）来协同执行。这种设计借鉴了人类专家团队的工作流，并引入了严格的对抗式审查机制，以确保调试过程的严谨性、深度与最终结论的可靠性。

### 4.1 架构选型：Multi-Agent 模型的必然性
在设计 AIRD Framework 的协作层时，一个根本性的问题是：应该采用单个具备多种能力的"全能" Agent，还是一个由多个"专才" Agent 组成的团队？我们最终选择了后者。
从渲染调试这一任务的本质属性来看，它天然满足 Multi-Agent 架构能够带来高收益的几个关键条件：
任务的高度可并行化：渲染调试并非一个线性的、单线程的过程。一个典型的复杂 Bug，例如由 GPU 驱动特定优化或着色器编译器精度降低（Precision Lowering）引入的视觉瑕疵，其根本原因可能潜藏在渲染管线的任何一个环节。为了高效定位问题，往往需要同时从多个维度展开调查：可以同时进行像素取证（Pixel Forensics）来追溯第一个出现问题的像素值，进行命令列表/事件流（Native Command List / Event Stream）的差分分析来定位异常的渲染通道（Pass），以及检查着色器代码与其中间表示（IR）来寻找潜在的逻辑错误。这些任务相互独立，可以并行执行，极大地缩短了调查周期。
对深度专业知识的依赖：渲染调试涉及的知识领域极其广泛，涵盖了图形 API、GPU 体系结构、着色器语言、编译器技术、驱动行为乃至特定硬件的特性。指望单个 Agent 精通所有这些领域是不现实的。一个由"管线代理"、"像素取证代理"、"着色器与中间表示代理"和"驱动/设备专家"等组成的团队，每个成员都具备深度的领域知识，能够进行更精准、更深入的分析。
避免上下文污染的需求：在复杂的调试会话中，单个 Agent 的上下文窗口会迅速被各种工具调用、代码片段、日志和中间结论所填满。如果让同一个 Agent 在分析像素值、检查 SPIR-V 代码和对比驱动版本之间频繁切换，其有限的上下文很容易被无关信息"污染"，导致其"注意力"分散，推理能力下降。Multi-Agent 架构为每个 Agent 提供了独立的上下文空间，使其可以专注于单一任务，保持推理的连贯性与深度。
#### 4.1.1 Claude Code Team Agents 机制的引入
我们借鉴了 Anthropic Claude Code 的 Team Agents 机制，因为它提供了一套成熟的、工程级的协作抽象，完美契合了渲染调试中"观点碰撞"和"互相挑战"的核心需求。该机制的核心组件包括：
Team Lead / Orchestrator：总协调者，负责任务分解、分派、进度跟踪与最终裁决。
Teammates：多个拥有特定技能的专家 Agent，每个 Agent 专注于特定领域的分析与诊断。
共享任务列表（Shared Task List）：所有 Agent 共享的任务队列，支持任务依赖与状态管理。
邮箱（Mailbox）：Agent 之间可直接消息通信的机制，支持观点交流与证据共享。
独立的上下文窗口（Independent Context Window）：每个 Agent 拥有独立的上下文空间，避免信息污染。
这比传统 Subagent 更适合 Debug 场景里"观点碰撞/互相挑战"的需求。

### 4.2 团队拓扑：7+1 专家角色
基于上述设计理念，我们为渲染调试任务定义了一个建议的"7+1"团队拓扑结构。这个结构中的每一个角色都对应调试工作流中的一个关键环节，并且可以被直接映射为 Team Agents 机制中的具体任务。其中，"+1"代表了至关重要的对抗式审查者（Skeptic），是保证调试质量的核心制度设计。

Multi-Agent 团队拓扑 - 展示 Coordinator 与 7 个专家 Agent 的协作关系，特别突出 Skeptic 的对抗式审查角色

#### 4.2.1 Skeptic 的核心价值
在这个团队结构中，Skeptic / Adversarial Reviewer 是一个至关重要的、不可或缺的角色。它的存在，是将人类专家在协作中"互相质疑、挑战彼此"的宝贵行为制度化。
在传统的调试流程中，一个看似合理但实际上错误的归因，一旦被提出并被初步接受，就很容易引导后续的调查走向歧途，浪费大量时间。Skeptic 的唯一职责就是对抗这种"确认偏见"（Confirmation Bias）。
Skeptic 的典型工作流程包括：
寻找反例：针对当前的根因假设，主动寻找可能的反例。例如，如果假设"问题是由 RelaxedPrecision 导致的"，Skeptic 会检查是否存在"使用了 RelaxedPrecision 但没有出现问题"的案例，或者"没有使用 RelaxedPrecision 但仍然出现问题"的案例。
挑战被遗漏的假设：检查调查过程中是否遗漏了某些可能的根因。例如，如果团队只关注了 Shader 代码，Skeptic 会提醒是否也应该检查资源数据、驱动版本、硬件特性等其他维度。
质疑证据链的因果关系：检查从现象到根因的推理链条是否严谨。例如，如果团队基于"A 发生后 B 发生"就推断"A 导致了 B"，Skeptic 会质疑是否存在其他可能的因果关系，或者是否只是巧合。
通过强制要求所有结论都必须通过 Skeptic 的"压力测试"，AIRD Framework 极大地抑制了"看起来正确"的草率归因，确保了最终输出的根本原因分析是健壮和可靠的。

### 4.3 协调机制：委托模式与质量钩子
一个高效的团队不仅需要明确的角色分工，还需要一个成熟的协调机制来保证流程的顺畅和产出的质量。AIRD Framework 在此借鉴并扩展了 Claude Code Team Agents 提供的两个关键机制：委托模式（Delegate Mode）和质量钩子（Quality Hooks）。

#### 4.3.1 委托模式（Delegate Mode）
为了避免 Team Lead / Orchestrator 陷入"既当裁判又当运动员"的困境，框架强制其在 Delegate Mode 下运行。
这意味着 Orchestrator 的核心职责被严格限制在协调和决策上：
任务分解与分派：将复杂的调试任务分解为多个子任务，并分派给相应的 Teammate。
进度跟踪与资源协调：监控各个子任务的进度，协调资源分配，处理任务依赖关系。
证据审查与汇总裁决：审查各个 Teammate 提交的证据，综合判断，做出最终裁决。
Orchestrator 被明确禁止亲自下场执行具体的调试任务，如运行工具、编写代码或分析数据。这种职责分离确保了 Orchestrator 能够保持全局视角，专注于维护整个调查的逻辑流和证据门槛，而不会因为陷入执行细节而分散注意力，从而保证了决策的客观性与战略性。
#### 4.3.2 质量钩子（Quality Hooks）
为了将上文表格中定义的"质量门槛"程序化、自动化地执行，AIRD Framework 利用了可编程的钩子（Hooks）机制。这些钩子可以拦截工作流中的关键事件（如 TaskCompleted），并执行预定义的验证逻辑。如果验证失败，钩子可以拒绝该事件，从而强制执行质量标准。
例如，可以实现以下质量钩子：
反事实验证钩子：在 Report & Knowledge Curator 尝试将一个 Bug 标记为"已解决"并生成 BugFull 之前，检查证据集中是否包含了至少一个成功的反事实验证记录。如果没有，则拒绝完成任务，并要求补充验证。
BugCard 完整性钩子：在任务最终完成时，检查生成的 BugCard 是否包含了所有必填字段（如 bug_family， invariants_broken， symptom_tags， trigger_tags， anchor， key_evidence， root_cause_one_liner， fix_one_liner， recommended_sop）。如果缺失，则拒绝完成，并要求补充。
Skeptic 审查钩子：在 Orchestrator 做出最终裁决前，验证 Skeptic Agent 是否已经签署了对当前证据链的审查意见。如果 Skeptic 提出的质疑尚未被有效回应，则拒绝裁决，并要求继续调查。
通过将质量门槛代码化为一个个独立的、可组合的钩子，AIRD Framework 将抽象的质量要求转化为了具体、刚性的系统约束，确保了每一次调试都遵循同样的高标准，从而使得整个框架的输出具有高度的一致性与可靠性。

## 五，工作流示例：从现象到修复的完整链路
为了更直观地展示 AIRD Framework 的实际运作，以下通过一个完整的案例，演示从现象观测到最终修复的全流程。


### 5.1 案例背景
项目：某移动端 3D 游戏，使用虚幻引擎，支持多种 Android 设备。
现象：在部分 Adreno GPU 设备上，角色皮肤渲染出现明显的颜色异常，表现为局部过暗或过亮，而在 Mali GPU 设备上渲染正常。

### 5.2 工作流执行
#### 5.2.1 阶段 1：Triage & Taxonomy
输入：用户提交的 Bug 报告，包含异常截图、设备型号（Adreno 630）、操作系统版本（Android 11）。
执行：Triage & Taxonomy Agent 分析截图与描述，将现象归类：
symptom_tags: [颜色异常， 局部过亮， 局部过暗]
trigger_tags: [Adreno GPU， Android 11， 角色皮肤]
初始 Invariant 候选：I-PREC-01（精度约束）、I-LIGHT-UNPACK-01（光照解包范围约束）
输出：初步分类结果，路由建议 SOP_Precision_RelaxedPrecision_Adreno。
#### 5.2.2 阶段 2：Capture & Repro
输入：场景信息、设备配置。
执行：Capture & Repro Agent 设计 A/B 对比捕获策略：
A（异常）：在 Adreno 630 设备上捕获渲染帧
B（基线）：在 Mali G76 设备上捕获渲染帧
确保两者使用相同的场景、相同的角色模型、相同的光照条件。
输出：A/B 截帧对，异常锚点定位到角色皮肤的 Deferred Shading Pass。
#### 5.2.3 阶段 3：Pass Graph / Pipeline
输入：A/B 截帧文件。
执行：Pass Graph / Pipeline Agent 进行 命令列表/事件流（Native Command List / Event Stream）差分分析，对比 A 与 B 的渲染管线：
发现在 Deferred Shading Pass 中，A 的输出与 B 存在明显差异
进一步定位到 LightingCalculation 子 Pass
输出：anchor(pass/event) = DeferredShadingPass.LightingCalculation。
#### 5.2.4 阶段 4：Pixel/Value Forensics
输入：Anchor、相关资源。
执行：Pixel/Value Forensics Agent 追溯像素历史：
选取一个异常像素（过亮），追溯其计算过程
发现在 LightingCalculation 中，Diffuse 分量的数值异常大（超出 [0，1] 范围）
定位到 First Bad Event：某个纹理采样操作
输出："第一个错误事件" = 纹理采样操作，数值证据 = Diffuse 分量超出范围。
#### 5.2.5 阶段 5：Shader & IR
输入：Shader/IR 代码、反射信息。
执行：Shader & IR Agent 分析 LightingCalculation 的 Shader 代码：
对比 A（Adreno）与 B（Mali）的 SPIR-V 编译结果
发现 Adreno 版本中，关键计算使用了 RelaxedPrecision 修饰符
追溯到 HLSL 源码，发现使用了 half 类型进行光照计算
识别出关键表达式指纹：half diffuse = tex2D(DiffuseMap， uv).rgb * lightColor;
输出：可疑代码指纹 + SPIR-V Decoration 差分证据。
#### 5.2.6 阶段 6：Driver/Device Specialist
输入：A/B 测试结果、IR 差分。
执行：Driver/Device Specialist 进行归因分析：
确认问题只在 Adreno GPU 上出现，Mali GPU 正常
分析 Adreno 驱动对 RelaxedPrecision 的处理：发现 Adreno 驱动更激进地降低精度，将 half 映射为 FP16，导致光照计算溢出
排除"内容必现"可能性：在 Mali GPU 上，相同的 Shader 代码不会导致问题
输出："驱动/编译器 vs. 内容"裁决 = 驱动特定问题（Adreno RelaxedPrecision 精度降低）。
#### 5.2.7 阶段 7：Skeptic 审查
输入：全量证据。
执行：Skeptic / Adversarial Reviewer 进行反证：
质疑：是否所有使用 half 的地方都会出现问题？
要求补充实验：在其他使用 half 的 Shader 中验证是否也存在精度问题
质疑：是否可能是纹理数据本身的问题？
要求补充验证：检查纹理数据的数值范围
输出：反证清单 + 需要补充的实验列表。
#### 5.2.8 阶段 8：补充验证
执行：团队根据 Skeptic 的要求，进行补充实验：
验证其他使用 half 的 Shader：发现部分 Shader 也存在类似问题，但不如 LightingCalculation 明显
检查纹理数据：确认纹理数据本身正常，数值范围在 [0，1]
输出：补充证据，确认根因为 Adreno RelaxedPrecision 精度降低。
#### 5.2.9 阶段 9：修复与反事实验证
执行：团队设计最小 Patch：
将 LightingCalculation 中的 half 类型替换为 float
或使用 Precision Fence 强制关键计算使用高精度
应用 Patch 后，在 Adreno 630 设备上重新测试：
颜色异常消失，渲染结果与 Mali GPU 一致
输出：反事实验证成功。
#### 5.2.10 阶段 10：Report & Knowledge Curator
输入：Action Chain、证据、Patch。
执行：Report & Knowledge Curator 生成 BugFull 与 BugCard：
BugFull：

root_cause.category_primary: Precision Issue
root_cause.blame(location): LightingCalculation Shader， line 42
fix.fix_type: Code Patch
fix.summary: "将光照计算中的 half 类型替换为 float，避免 Adreno GPU 上的精度降低导致溢出"
完整的 Action Chain、Evidence 集合、环境上下文
BugCard：

invariants_broken: [I-PREC-01]
symptom_tags: [颜色异常， 局部过亮， 局部过暗]
trigger_tags: [Adreno GPU， Android 11， 角色皮肤]
anchor: DeferredShadingPass.LightingCalculation
key_evidence: [SPIR-V Decoration 差分， Pixel History， 纹理采样数值]
root_cause_one_liner: "Adreno GPU 对 RelaxedPrecision 的激进处理导致光照计算精度不足"
fix_one_liner: "将关键计算的 half 类型替换为 float"
recommended_sop: SOP_Precision_RelaxedPrecision_Adreno
输出：BugFull + BugCard，更新 Invariant Library 与 SOP Library 索引。
### 5.3 案例总结
通过这个完整的案例，可以看到 AIRD Framework 如何将一个复杂的渲染问题，通过系统化的流程、多智能体的协作、严格的证据链与反事实验证，最终定位到根因并产出可靠的修复方案。整个过程不依赖于个人经验的"猜测"，而是基于不变量驱动的逻辑推理与证据驱动的实验验证，确保了调试的科学性与可靠性。

## 六，总结与展望
AIRD Framework通过引入不变量驱动推理、证据驱动实验、对抗式多智能体验证以及结构化知识沉淀，为渲染调试提供了一套科学、系统、可进化的解决方案。
框架的核心优势在于：
从经验到逻辑：通过 Invariant Library 将模糊的"渲染结果不对"转化为精确的"Invariant 被违反"，建立起从现象到根因的系统化推理路径。
从猜测到验证：通过强制要求反事实验证，确保所有根因结论都经过严格的因果关系验证，避免了未经验证的"猜测"污染知识库。
从个体到组织：通过 BugCard 与 BugFull 的双层结构，将个体经验转化为组织资产，实现调试知识的有效管理与高效复用。
从静态到进化：通过 Action Chain 记录与 SOP 自动生成，框架能够从每次调试中学习，持续优化调试策略，实现自我进化。
从单点到协作：通过 Multi-Agent 专家团队与对抗式审查机制，模拟人类专家团队的协作模式，确保调试过程的严谨性与结论的可靠性。
AIRD Framework 的设计理念不仅适用于渲染调试，也可以推广到其他需要系统性问题诊断的领域，如性能优化、系统故障排查、安全漏洞分析等。随着 AI 技术的不断发展，我们期待 AIRD Framework 能够不断进化，最终实现完全自主的智能调试，为开发者提供更强大的工具支持。
